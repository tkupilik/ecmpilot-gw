# Home Assistant / MQTT

Dashboard card: [vehicle status card and paste instructions](home-assistant/README.md)
([ready-to-paste YAML](home-assistant/vehicle-card.yaml)). Read-only, built-in
Markdown card with entity detail dialogs for SOC, ambient temperature and 12V SOC;
no HACS dependency or vehicle commands.

## Setup

Open the gateway web UI → **Home Assistant**. Set the MQTT broker hostname or
IPv4 address, port (default **1883**), optional username/password, and publication
value-check interval (**1–60 seconds**, default **1 second**). Enable MQTT and save.
Changed value snapshots are published at that cadence. Unchanged values get a
heartbeat every **max(15 seconds, configured interval)** to maintain availability;
they do not force Home Assistant history writes. Diagnostics update at 1 Hz
while BSI frames arrive and once per minute when BSI is silent.
It is **disabled by default**. Settings are stored in NVS (`gateway/ha_mqtt`),
survive OTA and reconnect MQTT on CPU0 without restarting the gateway.
The host field accepts a DNS name/IPv4 address, not a URI; transport is local
MQTT over TCP. Old compile-time broker/credential options are replaced by the web.

Status shows disabled, connecting, connected or connection failure. Passwords
are never returned in responses. An empty input preserves the saved password;
**Remove saved password** explicitly clears it. Failed validation/NVS commit
leaves live settings unchanged. Revision checks prevent overwriting another
browser's edits; retrying the same desired settings is idempotent.

## Vehicle observations

There are **47 observation/diagnostic entities** covering SOC/range, available electrical and
thermal observations, charging, preconditioning, 12 V battery, BSI state and data
age, doors/locks, trips/consumption, four native programs and charge-limit status.
Unsupported INFO measurements are not exported. Program times use the vehicle's
local clock; trip/consumption fields retain their candidate-validation status.
An additional **Refresh vehicle** MQTT button sends an explicit refresh request;
it is independent of vehicle-data availability. See [the command interface](home-assistant/commands.md).

Remaining entities retain their unique IDs. On reconnect, GW clears retained
HA discovery entries for the old demo sensor and these unavailable measurements:
HV battery voltage/current, minimum/maximum battery temperature, measured cabin
temperature, charging power and remaining charging time. Neither their values nor
their age attributes are published. This also applies to the optional HS1 profile.
12 V battery voltage remains available and requests one decimal place in HA.
Charging uses `immediate` / `delayed`, matching the app’s Delayed charging label;
the separate UDP protocol retains its internal `deferred` value.

Values use effective global varstore observations and the same scaling as UDP
(km, V, °C, %, kWh/100km). Last known values stay published when CAN sleeps.
Ordinary entities have no MQTT JSON attributes topic and set `force_update=false`:
Recorder writes value/availability changes instead of a new row whenever source
age advances. **Battery data age** is the single diagnostic entity containing an
**`age_s` map** for all fields, plus a **`received_at`** timestamp generated by HA.
It uses a separate topic, with no `state_class`. A real BSI 036 reception in
the last 2 seconds selects 1 Hz publication; otherwise it updates once per
minute. The existing raw BSI RX commit timestamp drives this, irrespective of
power-mode content (including standby/unknown codes). Force overrides do not
simulate reception. The publisher reevaluates this each tick, so resumed BSI
traffic cuts short the minute-long wait, bounded to at most one publication
per second. Outbox/allocation failures retry at that same bound.
Each field retains its own observation age; live BSI never renews old SOC.
Exclude this live-only diagnostic from Recorder using
[`home-assistant/recorder-exclude.yaml`](home-assistant/recorder-exclude.yaml).
The `diagnostic` category alone does not disable recording. Verify its entity ID
if renamed, merge the exclusion into any existing Recorder section and restart HA.
The updated dashboard card reads this map and computes current ages locally.
**Battery data age** uses the original SOC observation. Force is effective-valid
with age zero; releasing it restores the producer value and its original age.
Unknown/invalid/out-of-range values become JSON null; only that entity becomes
unavailable. No battery energy/capacity is invented. The stored
charging start stays visible in immediate mode too, matching the phone.

## Topics and availability

Node: `ecmpilot_gw_<12-digit station MAC>`, separate from LCD. Default topics:

- `ecmpilot/<node>/state`: JSON observation values only; QoS0, unretained.
  On connect, old retained measurements are replaced by a retained JSON
  placeholder containing only null values (including the legacy age map).
  HA therefore cannot restore stale vehicle values on a later subscription.
  No empty payload is published on this data topic; existing JSON templates
  must be able to parse the migration message. Live snapshots stay unretained.
- `ecmpilot/<node>/state/diagnostics`: SOC age plus the per-field `age_s` map;
  QoS0, unretained, 1 Hz with recent BSI RX / once per minute while silent.
  Only Battery data age subscribes here.
- `ecmpilot/<node>/status`: retained online/offline, QoS1, offline last will.
- `homeassistant/<sensor|binary_sensor|button>/<node>/<key>/config`: retained QoS1
  discovery, stable unique IDs and one device group.

The state/status prefix remains a build-time option, default `ecmpilot`.
Availability combines gateway online with a non-null value. Expiry is
**3 × configured interval + 15 seconds** (at least **195 seconds** for the
diagnostic, covering its idle minute interval) and detects a missing gateway/MQTT link,
not old vehicle data. See the official [MQTT sensor](https://www.home-assistant.io/integrations/sensor.mqtt/)
and [MQTT binary sensor](https://www.home-assistant.io/integrations/binary_sensor.mqtt/)
contracts used for discovery and attributes.

Live state and diagnostics begin after discovery publication completes. Value,
availability and diagnostic-attribute templates also accept empty/non-JSON
messages, non-object JSON and absent fields without template exceptions.
Missing boolean values become unknown, rather than falsely reporting OFF.

After installing this firmware, reconnect MQTT to replace the retained discovery
configs under the existing unique IDs. Reload the MQTT integration once to clear
legacy per-entity `age_s`/`stale` attributes still held by HA, and replace the
dashboard card with the current YAML. No device/entity deletion is necessary.

MQTT also accepts explicit `vehicle.refresh` requests on a dedicated command
topic and publishes correlated admission/terminal results. The callback only
queues requests; the UDP task owns the same command cache/admission path as the
phone, and TaskCan remains the sole physical transmitter. Passive telemetry,
discovery, reconnect and result queries do not request a refresh. Independently
enabled automatic vehicle refresh retains its own behavior. Preconditioning
and schedule writes are reserved for later validated MQTT operation adapters.

## Runtime and verification

MQTT client: CPU0, priority 3, stack 6144. Configuration/publisher: CPU0,
priority 1, stack 6144. No PSRAM. Discovery advances one entity per 100 ms and
retries a full 8192-byte outbox. Publications use nonblocking enqueue, including
`store=true` for QoS0. ESP-MQTT fragments larger payloads over its 1024-byte IO
buffer. Only the publisher owns client lifecycle; HTTP/event callbacks never
stop/start it. `/api/ha` GET/POST uses redacted responses and same-origin POST.

Tests exercise real telemetry/discovery, source ages, Force/release, passive no-CAN
requests, persistence/failure, revisions, password redaction/preservation/removal
and the actual embedded editor. ESP-IDF 5.3.2 compiles/links the real MQTT branch
in the normal firmware. No live broker, CAN transmission or device flash is
part of this verification.
MQTT command tests additionally cover duplicate suppression, shared phone/HA
Busy admission, boot/retained-message rejection, unsupported operations, button
templates and actual controller readback before success. Incoming payloads are
bounded to 512 bytes; two request and four response slots bound transport RAM.
