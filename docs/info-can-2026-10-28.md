# INFO CAN capture validation and battery signals, 2026-10-28

## Result

**SOC has a source-supported candidate on `0x3E0`, byte 0, unsigned percent. All 124 recorded samples are `0x46 = 70%`. The owner recalls approximately 69 or 70% SOC and 24.4 kWh available energy during these recordings. No supported remaining-battery-energy field in kWh was identified on INFO.** The recollection supports the SOC candidate at one operating point; it is not a synchronized diagnostic reference or proof of full-scale calibration. SOC and many other fields remain constant, and there is no simultaneous HS1/INFO trace. This does not prove that INFO never carries energy.

The [updated INFO DBC](../dbc/opel_corsa_e_info.dbc) retains the full source bus and covers **all 31,275 recorded frames / 105 observed IDs**. Six source DLCs are adapted to the observed lengths. An additional, source-unknown ID `7A4` is retained as eight raw bytes. No canonical source signal was removed: all source fields in the shortened `0A8` fit its actual four-byte prefix.

This verifies byte conversion, active mux branches, lengths and complete bit coverage. It **does not validate every physical meaning, source sender, enum, unit, range or availability condition**.

Every record is Rx, standard ID, viewer bus index 0. Bus index 0 is the capture channel label, not proof that this is the same physical bus as index 0 in the HS1 files. INFO files are selected explicitly; the generator never scans the mixed `logs/` directory indiscriminately.

The files retain their original frame order and negative absolute timestamps. Relative differences are interpreted as microseconds. There are **zero timestamp regressions in these three files**; clocks and period statistics never bridge files. The reader records any future regression as a new timing segment, without sorting frames or guessing a wrap modulus. In that case whole-file elapsed duration is left unavailable, and periods do not bridge the discontinuity.

## SOC

```text
INFO ID 3E0, DLC 8:
46 00 00 00 00 00 00 00

SOC candidate [%] = data[0]
DBC start 7, length 8, Motorola, factor 1, offset 0.
```

The DBC signal is **`BatterySocCandidate`** in **`ICSV_BatterySocAndHistory`**. `ICSV` is the first upstream sender alternative, not a measured physical transmitter; the source also lists BSI. The original source title `HYBRID_INFO`, signal name `BATTERY_STATUS`, all sender alternatives and the source unavailable code 127 remain documented.

For comparison, the older [obd_hscan1.csv](../logs/obd_hscan1.csv) contains HS1 `5C3` SOC **70.6..70.7%**:

```c
// HS1, not INFO; ten-bit value in 0.1 percent.
unsigned soc_x10 = ((data[2] & 0x03u) << 8) | data[3];
```

That earlier value is compatible with the later integer 70 on INFO. The owner's recollection of 69 or 70% also supports the observed value. The recordings are **not simultaneous**, so this does not establish rounding versus truncation, update latency or exact equivalence of BMS SOC and displayed SOC. A second operating point with a timed reference is needed to validate the full interpretation. A numerically valid byte also does not prove the data is fresh during a remote wake.

## Energy search and related fields

- Neither **HS1 `543`** (candidate remaining/total BMS energy) nor **HS1 `5C3`** (voltage/SOC) occurs in any of the three INFO files. The other pinned HS3 mapping of battery voltage/SOC, `22F`, is absent too.
- The pinned INFO source has no observed canonical field identifying remaining battery energy with an absolute Wh/kWh unit. No new energy signal has been invented from a constant word merely because its scaled value looks plausible.
- HS1 `543` uses two candidate 11-bit fields with factor 32 Wh. The same layout also appears in the local [Battery-Emulator CMP parser](../../battery_emulator_github/Battery-Emulator/Software/src/battery/CMP-SMART-CAR-BATTERY.cpp). That parser is corroboration of a **battery-side/HS1 layout**, not evidence of an INFO ID or physical energy accuracy in this car.
- **INFO `3A8` is not the six-byte HS1 `3A8` layout.** All 126 INFO samples are eight bytes, `FC FC FC 00 00 00 00 00`; the INFO source describes trip-duration fields, with the three leading components at their unavailable value. Reusing the HS1 consumed/relative-energy interpretation here would be unsupported.
- **`31A`** carries source-defined electric range, average consumption and charge scheduling. In the startup capture, the two average-consumption candidates become **21.5 and 20.7 kWh/100 km** at about 9.270 s. These are consumption rates, not remaining battery energy. The instantaneous-consumption field is unavailable (`raw 511`) throughout all three files.
- The low 11 bits of `31A`'s last two bytes change from **182 to 181 minutes** in the MyOpel capture, after the independently confirmed schedule update in [`35B`/`160`](../PSA_telematic.md). Thus `05 B0 -> 05 A8` is a corroborating **charge start time**, not an energy decrement. Do not treat those trailing words as kWh.
- **`3DA`** has a candidate time counter increasing 1500 -> 1527 during the startup capture. Its source-labelled distance counter is 617 -> 633, with two extra zero bytes beyond the source DLC. Its distance unit/meaning is not independently validated; neither this counter nor the extra bytes establishes remaining battery energy.
- **`396` SOC is labelled auxiliary/12 V battery SOC by the source**, not traction SOC. It must not replace `3E0` just because its percent value looks reasonable.

The unknown `7A4` changes between zero/binary data and payloads containing ASCII-like bytes (`02 30 30 35 33 00 00 03`, `05 30 30 32 38 00 00 03`). There is no verified ECU attribution, application protocol or energy meaning. The DBC therefore exposes raw bytes only.

### Numeric search using the owner's 24.4 kWh reference

The reference was used for a reproducible search in [search_info_energy.py](../tools/search_info_energy.py), with results in [energy-search JSON](../dbc/opel_corsa_e_info.energy-search.json). The search covers unsigned contiguous 8..16-bit fields, both BE and LE, zero offset and 15 explicit scales, including **32 Wh per count** from the HS1 energy layout and **1/64 kWh per count** used for diagnostic D865 by the [Android profile](../../android_dash/app/src/main/java/cz/ecorsa/dash/obd/EcmpProfile.kt).

The selected tolerance is **24.4 +/- 0.3 kWh**, an analysis window rather than a claim about the precision of the owner's recollection. A match must fall inside it on at least 90% of its samples, with at least 20 matching samples and representation in every input file. This limits the search to **82 shared IDs**; rare/event-only IDs, other widths/scales, nonzero offsets, signed or noncontiguous layouts are not ruled out.

There are **915 numeric field/scale hypotheses**, not 915 energy signals. Every match overlaps at least one nonreserved field in the current source description. Many are slices of defaults, VIN text or configurations. For example, bits spanning `161`'s constant `FD` oil-level code can be made to give exactly 24.4 with a scale of 0.1; that numeric equality is not evidence of battery energy. The source itself can contain errors, so overlap is a review annotation, not automatic rejection.

No hypothesis currently has enough independent support to add a new energy signal to the DBC. The raw-only added bytes also yield no stable match under these search conditions. A later capture at a different independently recorded energy/SOC provides the needed second operating point to reject the many static coincidences. Do not tune a scale to force the existing 70% SOC into 24.4 kWh: that would be a derived estimate, not discovery of an energy field.

## Source DLC discrepancies

These lengths are consistent across every occurrence in all three files:

| ID | Source DLC | Observed/exported DLC | Handling |
| --- | ---: | ---: | --- |
| `069` | 2 | 5 | Keep prefix fields; bytes 2..4 raw |
| `0A8` | 6 | 4 | All named source fields fit; remove only nonexistent raw suffix bytes |
| `165` | 5 | 6 | Keep source fields; additional byte raw |
| `329` | 7 | 8 | Keep source fields; additional byte raw |
| `364` | 6 | 7 | Keep source fields; additional byte raw |
| `3DA` | 4 | 6 | Keep source fields; two additional bytes raw |
| `7A4` | absent | 8 | Add `Unknown_InfoMessage01`, raw bytes only |

Byte indices in this table are zero-based. Preserving a fitting prefix is not confirmation that its semantic interpretation is correct. The complete original upstream definitions and alternatives are unchanged in [source JSON](../dbc/opel_corsa_e_info.source.json); observed lengths are recorded separately in the inventory and capture report.

Two source `can-tp` IDs occur: `2D4` (126 one-byte `00` records) and `328` (one eight-byte `10 0F 00 03 12 BD 44 41` record). Their DBC transport maximum is eight bytes, so `2D4` remains shorter by design and is decoded without padding. The static `00` alone does not establish a valid ISO-TP transaction or prove whether this car uses a direct application status on that ID. `328` resembles a First Frame declaring 15 bytes; no completed stream is established here. Raw conversion success must not be reported as validated ISO-TP communication.

## Semantic review remains separate

The range report retains source-invalid values, equality with source defaults, undefined enum codes, nonzero reserved fields and out-of-source-range values separately. Examples needing review include:

- `276 ClockYear` decodes to 2026, beyond the source's old maximum. This is a source-bound issue, not proof of bad vehicle data.
- Several unused equipment values are outside the nominal measurement range while matching a source default, e.g. `268 UreaTankLevel = 155%` at raw 31 and `1E8 ThermalPrecondClock = 1440`. Neither is a usable physical reading.
- Absent Eco Coaching uses repeated `0xE` nibbles; some source enum/default descriptions are incomplete.
- `0E0`/`2E0` unused schedule slots produce raw 2047 although the source does not explicitly label every such field invalid. Their meaning remains a candidate.

These observations do not justify deleting all fields of the affected messages. No field is promoted to verified just because its numeric result falls inside the source range.

```powershell
python tools/generate_info_can_dbc.py `

  --capture logs/infocan.csv `

python -m unittest discover -s tests -p test_info_can_dbc.py -v

python tools/search_info_energy.py `
  --capture logs/infocan.csv `
  --capture logs/info_apka.csv `
  --capture logs/info_start_jizda.csv `
  --reference-kwh 24.4 `
  --output dbc/opel_corsa_e_info.energy-search.json
```

The export contains **377 messages / 7,922 DBC signals**, including the 376-ID source baseline and the raw-only unknown ID. All actual frames decode without fabricating absent bytes; **579,906 individual signal values** are checked against independent extraction. Full coverage on all actual payloads is required. The report also compares the unadapted source baseline with the same inputs.

The unadapted source baseline covered all bits of **28,900 / 31,275 frames**; `7A4` was missing on 124 frames, and extra captured bytes on source-short messages were not described. The adapted export covers **31,275 / 31,275**. The range review flags **41 distinct fields** across the files for source-range, enum or reserved-bit review; flags are not automatic physical invalidation. Ten tests pass, including clock discontinuities and independent files with identical basenames.

For remaining energy, the useful next capture is simultaneous INFO and HS1 while SOC changes, with a dashboard/UDS energy reading as an independent reference. Include the period around a `394` refresh and charging or a sustained load. This allows correlation of real energy changes rather than guessing from one constant SOC point. These tools perform no CAN transmission and add no firmware mappings.
